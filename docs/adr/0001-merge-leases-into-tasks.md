# ADR-0001: Merge `leases` table into `tasks`

Date: 2026-05-04
Status: Accepted

## Context

The current schema (SPEC §3.4) models lease ownership as a separate `leases`
table. Each scheduler dispatch INSERTs a new row; reaper / finalize sets
`released_at = now()`. The table serves three roles simultaneously:

1. **Slot accounting ledger** — `count(leases WHERE released_at IS NULL)` is
   how the scheduler knows how many CPU/SSH/training slots are in use
   (`lib/scheduler.ts:99-107`).
2. **Fencing token** — the BullMQ message carries `leaseId`; `claimTask`
   gates on `EXISTS (SELECT 1 FROM leases WHERE id=$3 AND task_id=$1 AND
released_at IS NULL)` (`lib/worker.ts:115-118`) to reject stale
   deliveries.
3. **History** — every dispatch attempt leaves a row with
   `acquired_at / heartbeat_at / released_at`, allowing post-hoc audit.

For this project (a single-developer learning lab — see CLAUDE.md and
SPEC §1) role 3 is not load-bearing: there is no audit, billing, or SLA
consumer of lease history; `tasks.failure_reason` plus `tasks.attempts`
are sufficient for debugging. Roles 1 and 2 can be expressed as columns on
`tasks` because **at most one active lease per task** is an existing
invariant (one task in `queued`/`running` is owned by at most one worker).

The proposal is raised now because (a) Phase 4 (T15 fairness panel, T16
verification) hasn't been implemented yet, so the cost of changing the
fairness query and dashboard data shape is still bounded; (b) the
discussion in `tasks/todo.md` Phase 5 (multi-process scaling) will fork
the worker process layout, and a simpler lease model reduces the surface
area of that future change.

Tasks completed under the current model whose acceptance criteria
explicitly reference `leases`: T2, T5, T6, T7, T8, T10.

## Decision

Drop `leases` and represent current ownership as three columns on `tasks`:

```sql
ALTER TABLE tasks
  ADD COLUMN lease_token        uuid,
  ADD COLUMN lease_expires_at   timestamptz,
  ADD COLUMN lease_heartbeat_at timestamptz;

CREATE INDEX tasks_lease_expires_idx
  ON tasks (lease_expires_at)
  WHERE lease_expires_at IS NOT NULL;
```

Semantics:

- `lease_token IS NULL` ⇔ task has no active lease (pending / succeeded /
  failed, or just-reaped queued/running). The token is generated by the
  scheduler at `reserveOneTask` and overwritten on every fresh dispatch.
- `lease_expires_at` and `lease_heartbeat_at` replace the same-named
  columns on `leases`. Heartbeat UPDATEs only these two fields, which are
  not indexed → Postgres HOT update path applies; tasks bloat is bounded.
- "Release" is `SET lease_token = NULL, lease_expires_at = NULL` (in the
  same UPDATE that flips status to `succeeded` / `failed` / `pending`).

Operation rewrites:

- **Slot accounting** (`countActiveLeases`):
  `count(*) FROM tasks WHERE kind=$1 AND lease_token IS NOT NULL AND lease_expires_at > now()`
- **Fairness ordering subqueries** (`reserveOneTask`): same shape, but
  count over `tasks` self-join (eliminates the JOIN to `leases`).
- **Reserve transaction**: collapses INSERT lease + UPDATE task into a
  single UPDATE that sets `status='queued', lease_token=$new_uuid,
lease_expires_at=now()+TTL, lease_heartbeat_at=now()`.
- **Claim** (`claimTask`): the EXISTS subquery is replaced by
  `lease_token = $messageToken`. `attempts = $expectedAttempts` and
  `status = 'queued'` checks remain; this is a defence in depth — the
  named token makes intent explicit, attempts catches the case where a
  bug accidentally leaves the token unchanged across reaps.
- **Heartbeat**: `UPDATE tasks SET lease_heartbeat_at=now(),
lease_expires_at=now()+TTL WHERE id=$1 AND lease_token=$2`. The
  `lease_token` predicate replaces today's `released_at IS NULL` guard —
  a released lease has `lease_token=NULL`, so the UPDATE is a no-op.
- **Reap**: `SELECT id, attempts, max_attempts, job_id FROM tasks WHERE
lease_expires_at < now() AND status IN ('queued','running')
FOR UPDATE SKIP LOCKED` — uses `tasks_lease_expires_idx`. Branches
  unchanged (retryable → pending; terminal → failed + failJob).
- **BullMQ payload**: `DispatchMessage.leaseId` renamed to `leaseToken`.

The `attempts`-as-fencing-token argument explored in earlier discussion
is rejected: an explicit `lease_token` keeps fencing local (does not
depend on the "reaper does not bump attempts" invariant holding across
future commits) and yields clearer claim-rejection logs.

## Consequences

- **Positive:**
  - One fewer table, three fewer indexes; schema fits the mental model
    ("lease is task ownership metadata").
  - `reserveOneTask` collapses from SELECT + INSERT + UPDATE to SELECT +
    UPDATE inside its transaction — fewer round trips, smaller window
    for the scheduler advisory-lock contention.
  - Fairness query no longer JOINs `leases`; uses existing
    `tasks_kind_status_user_idx` for the count subqueries.
  - `docs/task-lifecycle.md`'s "running → queued puzzle" simplifies
    because the lease no longer has its own released_at axis to reason
    about; the puzzle becomes a one-table state machine.

- **Negative:**
  - Lease history is lost. Each dispatch overwrites the previous
    `lease_token / lease_expires_at / lease_heartbeat_at`. If a future
    requirement needs per-attempt timing, a separate `task_attempts`
    table will need to be reintroduced.
  - Heartbeat UPDATEs now hit `tasks` rows. As long as the new lease
    columns are not indexed (only the partial `lease_expires_at` index,
    which is sparse), Postgres HOT updates apply and bloat impact is
    bounded — but it is non-zero compared to writing to the smaller
    `leases` table.
  - The reap query joins `tasks` directly. The new partial index keeps
    it sparse, but as `tasks` grows, autovacuum on the index has more
    work than today's tiny `leases_resource_released_idx`.
  - Migration is destructive; existing lease rows in any running
    instance are dropped. Acceptable given `pnpm db:reset` is the
    standard workflow for this lab.

- **Neutral:**
  - Fencing strength is unchanged. `lease_token` is a uuid (same as
    today's `lease.id`); the only difference is which row it lives on.
  - Crash safety of T5's "scheduler dies between commit and BullMQ add"
    is preserved: the task is left as `status='queued'` with a live
    `lease_expires_at`, the reaper picks it up exactly as before.
  - SPEC §3.9 (single-instance scheduler) is unaffected — advisory
    lock layer doesn't care about lease layout.
  - SPEC §3.10 (BullMQ lockDuration alignment) is unaffected.

## Alternatives considered

- **Keep current approach** (independent `leases` table): simplest
  no-op. Falls short because (1) the table earns its complexity only via
  the history role, which has no consumer in this lab; (2) the four-axis
  state interaction (task.status × task.attempts × lease.released_at ×
  lease.expires_at) is harder to teach than the three-axis equivalent.

- **Drop `lease_token` and use `attempts + status` as fencing token**
  (the "minimum schema" variant): rejected because it makes correctness
  depend on the global invariant "only `claimTask` increments attempts."
  Future commits could plausibly violate this (e.g. "reaper bumps
  attempts on permanent failure" feels reasonable in isolation) and
  fencing would silently degrade. An explicit token is cheap insurance.

- **Two-phase split: `slot_reservations` (scheduler-side) + `leases`
  (worker-side)**: cleanest semantically — scheduler doesn't pretend to
  hold a "lease" — but introduces _more_ moving parts than today,
  not fewer. Worth revisiting only if the multi-process Phase 5 ends up
  needing per-process worker identity tracking.

## Notes for replan

Tasks expected to need amendment:

- **T2** (schema): rewrite `db/schema.sql` and acceptance criteria to
  reflect new `tasks` columns + dropped `leases`.
- **T5** (scheduler tick): update fairness SQL (count subqueries),
  collapse reserve into single UPDATE, replace `INSERT lease`. Update
  `DispatchMessage` type.
- **T6** (CPU worker): update `claimTask` to use `lease_token`; update
  `releaseLease` to NULL out the columns; update finalize transactions.
- **T7** (SSH worker): same shared helper changes; verify barrier still
  works (it doesn't touch leases directly — should be untouched).
- **T8** (training worker): same shared helper changes.
- **T10** (heartbeat + reaper + failure propagation): heaviest rewrite.
  New heartbeat SQL; new reap query targeting tasks; failJob branch
  unchanged.
- **T15** (fairness panel — not yet built): API derives from
  `tasks.lease_*` instead of `leases`. Update task description before
  starting.

Tasks expected to be rolled back: none (the existing tasks stay in
`todo.md` as completed, but their semantics change — Checkpoint A and B
human-review boxes should be re-checked once the new schema is verified).

New tasks expected:

- **T-MIG**: schema migration + helper rename (`leaseId` → `leaseToken`)
  across `lib/worker.ts`, `lib/scheduler.ts`, `lib/queues.ts`,
  `worker/*.ts`, and all touched tests.
- **T-RACE**: race-condition test for "dispatch → reaper expire →
  re-dispatch → two BullMQ messages claim concurrently" — explicit
  coverage that the new `lease_token` fencing closes the same window
  the old `EXISTS (SELECT FROM leases ...)` closed.
